# ☁ MCSync · Minecraft 存档云同步工具

一套「Linux 服务端 + Windows 客户端」的 Minecraft 存档云同步方案：自动识别 PCL2 / HMCL / 官方 / Prism / MultiMC / Modrinth 的实例与存档，按 4 MiB 内容寻址分块做增量同步，带版本快照、冲突处理与 Web 管理页。

## 零之二、整合包配置同步

存档之外，实例的 `config/` 目录也可以单独同步 —— 里面放着模组与服务端配置。
多人玩同一个整合包时，只有配置也一起同步，各人的世界表现才不会跑偏。

- 本地页选中实例后点「⚙ 同步整合包配置」上传
- 云端列表里带 `⚙ 整合包配置` 标记，选中后下载会装到本机同名实例的 `config/`
- 不同整合包的配置各自独立，互不覆盖
- 客户端自身配置（不属实例）不参与同步

## 零之三、账号与权限

服务端采用**账号登录 + 两级权限**，客户端不再用服务器随机口令连接。

| 角色 | 客户端 | 管理面板 |
|---|---|---|
| 管理员 | 完整功能 | 全部权限：管理云端存档（删/回滚/改名/归类/清理）+ 账号管理 |
| 普通用户 | 完整功能（上传/下载/版本管理） | 只读浏览 |

**没有自助注册**——账号只能由管理员在面板「账号管理」里创建，
拿到服务器地址的人无法自行进站。

**首次使用流程**：

1. `sudo bash deploy.sh`，记下输出的 **管理员密钥**（16 位）
2. 浏览器打开管理页，用这串密钥**创建第一个管理员账号**
3. 之后一律用账号登录；在「账号管理」里给其他使用者开号
4. Windows 客户端「设置」里填 **账号 + 口令** 连接

口令用 PBKDF2-HMAC-SHA256 加盐存储（20 万次迭代），不存明文。
管理员停用或删除账号后，该账号下所有设备**立即失效**。
最后一个管理员不可被降级或删除，避免系统失去管理能力。

```
server/accounts.py    # 账号存储与口令哈希
server/auth.py        # 鉴权：账号 → 会话 / 客户端私钥签名
```

## 零之四、界面语言

设置 → 外观里可切换 **简体中文 / English**，重启客户端后完全生效。

实现要点：源码里的字符串本身就是中文，所以中文模式原样返回、无需维护词条；
英文模式查表，未翻译的自动退回中文（不会出现空白或占位符）。
新增界面文案时只需往 `client/core/i18n.py` 的 `_EN` 里加一条。

## 零之五、登录与设计规范

**登录**：打开软件第一屏就是登录窗口（不是藏在设置里）。
可勾选「记住口令，下次自动登录」。口令存于系统加密区（Windows 走 DPAPI），
配置文件里不留明文。不登录也能管理本地存档，只是云同步不可用。

**设计规范**：界面数值全部来自 `client/ui/design.py` 的设计令牌——
间距只能用 4/8/12/16/24/32，字号分 H1/H2/正文/次要/说明五档，
圆角与尺寸同样走刻度。改一处即可全局生效，不会再出现随手填数值导致的版面松散。
配色对比度按 WCAG AA 校验（正文 ≥4.5:1）。

**启动性能**：实例列表先秒出（只读 level.dat），体积后台补；
重扫结果与现有列表一致时不重建界面，避免连锁重新加载。

## 零之六、区块清理（按 InhabitedTime）

侧栏「🧹 区块清理」页可以按**玩家在区块内的累计停留时间**筛选并删除区块，
用来清掉"生成了但没人待过"的探索痕迹，给存档瘦身。

**默认阈值 = 停留不足 1 秒**（`InhabitedTime < 20 tick`）。这个条件非常保守：
只有刚生成就离开的区块会命中，基本不会误删有建筑、箱子或下界传送门的区域。
阈值可在页面上调整（秒）。

### 安全设计

| 机制 | 说明 |
|---|---|
| 默认只预览 | 点「扫描预览」**一个字节都不改**，只出报告：命中区块数、按维度分布、涉及文件、预计释放空间 |
| 二次确认 | 看过报告后点「执行清理」，还要再过一次确认弹窗 |
| 强制备份 | 执行前自动把整个存档硬链接备份到 `_MCSyncBackups/` |
| 游戏关闭检查 | 检测到 `session.lock` 被占用会拦截，避免读到写入中的区块 |
| 三目录协同 | `region/` / `entities/` / `poi/` 按同一全局区块坐标一起清理，不留孤立实体与 POI |
| 多维度 | 主世界、下界、末地、自定义维度分别列出，可单独勾选 |
| 多整合包 | 顶部「游戏实例」下拉切换即可处理其他整合包，每个实例独立列出自己的存档 |
| 云端可回滚 | 清理的是本地文件；云端历史版本仍在，必要时从版本管理回滚 |

### 与 MCA Selector 对齐的实现细节

参考了开源项目 [Querz/mcaselector](https://github.com/Querz/mcaselector)
（`io/WorldDirectories.java`、`io/mca/CompressionType.java`、`io/mca/MCAFile.java`）：

- **世界目录检测**：只要找到 `region` 文件夹就当作一个可处理世界，
  `poi` / `entities` 可选；不对整合包或维度名做白名单。因此经典
  `region` / `DIM-1` / `DIM1`、1.16+ 的 `dimensions/<ns>/<name>/region`、
  以及 26.1 的 `dimensions/minecraft/overworld|the_nether|the_end/region`
  都会被递归识别，自定义维度也照常列出。
- **压缩类型字节**：`NONE 0` / `GZIP 1` / `ZLIB 2` / `UNCOMPRESSED 3` / `LZ4 4`；
  最高位（Java 里是负 byte）表示 chunk 数据放在外部 `.mcc` 文件，低 7 位仍是
  上述算法。四种常规压缩都能读出 `InhabitedTime`。
- **能力检测**会遍历**所有维度**并只抽样 `.mca` 文件。旧版只取目录列表前 8 项、
  且第一个维度样本够了就提前退出：`region` 目录里混着 `.mcc` 时一个区块都读不到，
  整个存档被误判成「不支持」——表现就是「多个整合包只有一个能清理」。已修复。
- **外部 `.mcc` 标记**的 region 整份不参与清理，但原始扇区字节完整保留，
  绝不因为读不懂就丢掉玩家数据。

### 真实区块 NBT 兼容性（为什么之前「只有一个整合包能用」）

这是最容易踩、也最难查的一处：`core/nbt.py` 里 `TAG_Byte` 曾写成条件表达式，
**负 BYTE 会多读一个字节**。而 1.18+ 的 `sections[].Y` 从 **-4** 开始（字节
`0xFC`），必然触发 —— 整份 NBT 解析流错位，报「未知 TAG 类型 252」，所有区块
被标成「无法解析」，`capability()` 于是把**整个存档**判成格式不兼容并禁用。
只有恰好没踩到负 BYTE 的那个整合包能用，表现就是「MCA Selector 全能操作，
本项目只有一个能用」。

现在改成三级解析，并加了 `tools/test_chunk_prune_real.py` 锁死这个回归：

| 层级 | 作用 |
|---|---|
| `core/nbt_scan.py` | 轻量扫描器：只遍历根 / `Level` 的直接子项，命中 `InhabitedTime` 立刻返回，其余用 `skip_payload` 流式跳过，**不构建整棵 NBT 树** |
| `core/nbt_typed.py` | 保类型解析器回退 |
| `core/nbt.py` | 通用解析器回退（负 BYTE 的一行 bug 已修） |

配套改进：

- **压缩全覆盖**：`NONE 0 / GZIP 1 / ZLIB 2 / UNCOMPRESSED 3 / LZ4 4`，
  LZ4 用纯 Python 实现兜底，Windows 客户端不需要额外装 `lz4` 包
- **前缀解压**：`InhabitedTime` 位于 NBT 前部，只解压前 64KB；字段靠后或损坏时
  自动全量重试，绝不会把「没解压完」当成「没有该字段」。实测 16MB 存档的
  预览从 **13 秒降到 0.47 秒**
- **判定不再一刀切**：只有「NBT 完整解析成功、且确实全都没写该字段」才判低版本
  禁用（这是你要求的）；个别区块读不懂只标记保留，不牵连整个存档
- **页面显示具体诊断**：识别几个维度、抽样几个 region、可读 / 缺字段 / 不可读 /
  外部 `.mcc` 各多少区块。再出问题时不用猜，直接看数字

`tools/test_chunk_prune_real.py` 构造了 1.12.2 / 1.16.5 / 1.20.1 / 1.21.1 /
26.1 五种版本的真实风格区块（含负 BYTE、`LongArray`、嵌套 `List<Compound>`），
逐个验证能力检测、筛选、压缩解析、执行后字节还原，41 项全过。

### 低版本存档自动禁用

`InhabitedTime` 不是所有版本都写。若整个存档**一个区块都读不到该字段**，
页面会直接禁用扫描与执行，并说明原因 —— 绝不把"没有字段"当成"没人来过"。

1.17 及以前把该字段放在 `Level.InhabitedTime`，工具同样能识别。

### 无法判定的区块一律保留

以下情况会**跳过并保留**，报告里单独列出数量，绝不删除：

- 压缩算法不认识（LZ4 / 自定义 ID 127 / 外部 `.mcc` 存储）
- NBT 损坏、长度头截断、数据越界
- 字段缺失

> 若存档使用 LZ4 压缩（部分服务端配置），安装 `lz4` 包后可正常识别；
> 未安装时这些区块会被安全保留，不影响其余区块清理。

### 清理后

文件会被**紧凑化重写**（清表项 + 回收数据区空隙），空 region 文件直接删除，
体积真的会变小。记得把清理后的存档**上传到云端**，其他人下载时才会拿到新版本。
region 内部差分已适配：改动只会让少量分片失效，重传量很小。

⚠ 删除后地形会按世界种子重新生成，边界处可能与周围生物群系不连续。
阈值只是"是否有人用过"的参考线索，不是安全判据 —— 建议先备份、先看预览地图范围，
下界尤其谨慎（传送门、要塞常常停留时间很短但很重要）。

## 零之七、共享玩家数据（不用装模组）

**解决那个经典坑**：房主把单人存档共享给别人，接手者打开世界会变成房主的
背包、位置、经验和进度，甚至把自己的角色数据覆盖掉。

原因是 Java 版 26.1 之前，单人世界把「世界所有者」的完整玩家数据额外存在
`level.dat → Data → Player`，单人模式无条件优先读它，**完全不看当前玩家 UUID**
（Mojira MC-697）。26.1 起换成 `singleplayer_uuid` 指针，数据统一放
`players/data/<UUID>.dat`，但指针仍可能指向房主。

MCSync 在**客户端侧直接改存档文件**，不用为 Forge / Fabric / NeoForge
和每个 MC 版本分别编译模组：

| 步骤 | 行为 |
|---|---|
| 归档 | 把 `Data.Player` 写成独立的 `playerdata/<原主人UUID>.dat` —— 房主再打开时按自己 UUID 就能读回来，**数据不丢** |
| 摘除 | 从 `level.dat` 删掉 `Data.Player`（26.1+ 则删掉 `singleplayer_uuid`） |
| 结果 | 游戏退回按各自 UUID 读取玩家数据：A 读 A 的，B 读 B 的，没有就新角色进世界 |

**最大的好处是不需要知道当前玩家是谁**。模组要在游戏进程里拿登录 UUID，
独立程序拿不到；而「归档 + 摘除」对房主和接手者都成立，所以零配置即可工作。

### 用法：上传时自动完成，不需要手动操作

**默认开启**：每次「上传」前自动执行归档+摘除，所以**云端版本天生就是共享友好的**，
别人下载后直接是自己的角色。不需要任何人去点修复按钮。

- **本地存档卡片右侧的「🪪 UUID 修复」按钮**：只想让本机这份存档直接给别人打开、
  不想上传云端时，点它即可就地清除 `level.dat` 里的房主 UUID / `singleplayer_uuid`
  指针（同样会先归档、再备份）。**纯本地操作，不联网、不改云端版本**；
  上传时自动处理的功能完全保留，两条路径互不影响。
  已是共享友好、或游戏正开着时会明确提示并跳过，执行前需二次确认。
- 设置 → 同步 → 「上传前自动摘除房主玩家数据」可关闭（关闭后上传/下载都原样）。
- 下载时保留一层**兜底**：若云端是历史版本、仍带着内嵌房主数据，下载后自动修一次
  （幂等，正常情况不会触发）。
- **🪪 玩家数据页**只保留必要内容：自动处理状态、「我的 UUID」、处理结果输出，
  以及**对已经上传到云端的存档做补修**——选中云端存档 → 二次确认 →
  拉取最新版本 → 修正 → 上传为新版本。原版本保留可回滚，其他人重新下载即可。
- **我的 UUID（可选）**：填上后，若内嵌数据本就属于你则原样保留不动；
  留空时一律归档+摘除（房主数据会被归档回来，同样不丢）。

### 安全设计

- 改前把原始 `level.dat` 备份到 `<存档>/.mcsync/playerdata_backup/`
  （该目录默认不参与同步），同内容备份自动去重，最多保留 8 份
- 临时文件 + `os.replace` 原子写回，不会写出半截 `level.dat`
- 用保类型 NBT 读写器，12 种 TAG（含空 List 的元素类型、IntArray/LongArray）
  语义级完整保留，`level.dat` 其余字段一个不动
- 读不出原主人 UUID 时，**不伪装成任何玩家的数据文件**，而是把整份内嵌数据
  另存到 `.mcsync` 备份区，绝不丢数据也绝不顶掉别人的角色
- 目标 `.dat` 已存在且是真实数据时保留；只有「空壳」才备份成
  `.spd_backup` 后覆盖（该后缀已被默认忽略规则排除）
- `level.dat_old` 一并摘除，避免恢复流程把它读回去
- 游戏运行中（`session.lock` 被占用）拒绝修改
- **完全幂等**：第二次运行检测不到内嵌数据，直接跳过，不会来回震荡

### 多人协作时的流转

A 上传（自动摘除 + 归档）→ 云端版本已是共享友好 → B 下载直接是自己的角色，
且 B 也拿到 A 那份归档数据（按各自 UUID 读取，互不覆盖）→ B 玩完再上传同理。

> 旧版本上传的存档若还带着房主数据，用「🪪 玩家数据 → ☁ 处理云端存档」
> 补修一次即可；在那之前别人下载时也会走兜底自动修（结果相同、幂等）。

⚠ 26.1+ 的存档目录结构变了（`players/data`），核心同步模式已把 `players/`
纳入范围；旧版 `playerdata/` 照常支持。

## 零、推送到 GitHub

仓库内已提供一键脚本，双击 `push.bat` 即可：

```bat
push.bat                     :: 交互确认后提交并推送
push.bat -m "修复某问题"      :: 指定提交信息
push.bat --dry-run           :: 只做检查，不提交不推送
push.bat -y                  :: 跳过确认直接推送
push.bat -f                  :: 首次推送就强制覆盖远端
push.bat --no-force          :: 被拒绝时不自动覆盖，改为提示手动处理
```

**默认行为**：远端若有本地没有的提交（例如新建仓库时 GitHub 自动生成的 README），
脚本会**自动用本地覆盖**，并以 `--force-with-lease` 优先（比 `--force` 安全，
能防止误覆盖别人在这期间推上去的新提交）。单人维护场景这是最省事的选择。
若仓库变为多人协作，请加 `--no-force` 关掉这个行为。

脚本会在提交前做**安全扫描**，命中的文件一律拦下（口令、私钥、用户存档、
编译产物、数据库）。`.gitignore` 已排除同类文件，扫描是第二道闸。

```
├── push.bat                 # 一键推送（Windows）
├── push.py                  # 推送逻辑（含安全扫描）
├── .gitignore               # 忽略规则
├── .gitattributes           # 行尾规则（.bat 强制 CRLF / .sh 强制 LF）
└── LICENSE                  # GPLv3 全文
```

## 二、服务端一键部署（Linux）

把整个 `mcsync` 目录传到服务器（或 `git clone`），然后：

```bash
cd mcsync/server
sudo bash deploy.sh
```

脚本会自动检测：有 Docker 就走 **Docker Compose**，没有就走 **Python venv + systemd**。

### 常用参数

| 参数 | 说明 |
|---|---|
| `--mode docker` / `--mode native` | 强制指定部署方式 |
| `-p, --port 9000` | 改监听端口（默认 8650） |
| `-d, --dir /opt/mcsync` | 改安装目录（数据在其下的 `data/`） |
| `-k, --keep 10` | 每个存档最多保留 10 个版本（0 = 不限制） |
| `--verify` | 服务端校验上传块的哈希（更安全，但更耗 CPU） |
| `--status` | 查看运行状态与健康检查 |
| `--uninstall [--purge]` | 卸载服务（`--purge` 连数据一起删） |

### 部署后的常用命令

```bash
# Docker 模式
cd /opt/mcsync && docker compose logs -f && docker compose restart

# 原生模式
journalctl -u mcsync -f
systemctl restart mcsync
```

浏览器打开 `http://服务器IP:8650` 即可进入 **Web 管理页**：查看存档与版本、下载整包 zip、回滚、删除版本。

> 云服务器记得在安全组放行端口；生产环境建议用 Nginx 反代 + HTTPS。

## 二之二、服务端数据迁移（换服务器）

**一句话：要搬的只有两个东西 —— `/opt/mcsync/data/` 整个目录 + `/opt/mcsync/mcsync.env` 一个文件。**
源码、venv、static、systemd 单元都不要搬，新机器跑一次 `deploy.sh` 会重新生成。

### 数据目录里都有什么

| 路径 | 内容 | 漏了会怎样 |
|---|---|---|
| `mcsync.db`（+ `-wal` / `-shm`） | 存档索引、版本、审计日志、回收站记录 | **存档列表全空** |
| `blobs/` | 内容寻址数据块，全部存档的真实内容 | 能看列表但下载/回滚全部 404 |
| `manifests/` | 每个版本的文件清单 | 下载时无法组装 |
| `trash/` | 软删除的回收站 | 回收站里的存档消失 |
| `accounts.json` | 账号与加盐口令哈希 | **所有账号丢失**，只能重建 |
| `clients.json` | 已配对客户端记录 | 所有客户端要重新登录 |
| `token.txt` | 管理员密钥 | 管理页无法创建首个管理员 |
| `mcsync.env`（在**安装目录**，不在 data 里） | 端口、管理员密钥、IP 白名单、鉴权开关 | 重新部署会生成**新端口 + 新密钥**，所有人要重配 |

> `mcsync.env` 是最容易漏的一个：它不在 `data/` 里，但它决定了端口和口令。
> `deploy.sh` 的 `setup_credentials` 会读现有 env 里的 `MCSYNC_PORT` /
> `MCSYNC_TOKEN` / `MCSYNC_ALLOW_IPS`，**只要这个文件在位，重新部署后端口和
> 管理员密钥完全不变**。

### 一键迁移（推荐）

部署时脚本已把两个工具装到 `/opt/mcsync/`，换服务器时不用回头找源码包。

**旧服务器：**

```bash
sudo bash /opt/mcsync/migrate_backup.sh
```

它会自动停服务 → 打包 → 恢复服务，产出 `mcsync-migrate-时间戳.tar.gz`
和同名 `.sha256`。**停机是必须的**：SQLite 开了 WAL，不停机直接拷会拿到
不一致快照（`db-wal` 里还有未合并的事务）。如果已经手动停了服务，加
`--no-stop`；数据目录自定义过就用
`DATA_DIR=/your/path sudo -E bash ... --no-stop`。

打包用硬链接优先，几十 GB 的 `blobs/` 不需要额外一倍磁盘空间；跨文件系统
会自动回退到真实复制。`data/tmp/`（临时 zip 产物）不会带走。

**传到新服务器**（两个文件都要）：

```bash
scp mcsync-migrate-*.tar.gz* root@新服务器IP:/root/
```

**新服务器：**

```bash
sudo bash migrate_restore.sh --archive /root/mcsync-migrate-XXX.tar.gz
sudo bash deploy.sh
```

`migrate_restore.sh` 会校验 sha256、解包、把数据和 env 放到位、修正属主。
如果新机已经跑过一次部署、目录里有个空数据库，它会**拒绝覆盖**以防误删，
确认是空环境后加 `--force` 即可。

最后：

```bash
sudo bash deploy.sh --status     # 看真实公网地址与端口
```

在云控制台安全组放行该端口，然后让所有人在客户端
「设置 → 服务器地址」改成新服务器地址。

### 迁移后客户端要做什么

- **env 一起搬了**（默认情况）：端口和口令不变，`accounts.json` /
  `clients.json` 也在 → 客户端**只需改服务器地址**，不用重新登录、不用
  重新配对。客户端私钥存在本机系统目录（`%LOCALAPPDATA%\MCSync`），
  服务端配对记录还在，签名校验照样通过。
- **env 没搬**（Docker 自定义部署常见）：端口和密钥会重新随机生成 →
  所有人要改地址**并重新登录**。restore 脚本会明确提示这一条。

> ⚠ 客户端私钥用 Windows DPAPI 加密，绑定「本机 + 当前用户」。
> 换电脑 / 重装系统 / 换 Windows 账户时，即使服务端记录还在也得重新登录，
> 这是预期行为，不是故障。

### 手工迁移（不用脚本时）

```bash
# 旧机
sudo systemctl stop mcsync
sudo tar -czf mcsync-data.tar.gz -C /opt/mcsync data mcsync.env
sudo systemctl start mcsync

# 新机
sudo mkdir -p /opt/mcsync
sudo tar -xzf mcsync-data.tar.gz -C /opt/mcsync
sudo bash deploy.sh
sudo chown -R mcsync:mcsync /opt/mcsync   # deploy.sh 也会做这一步
```

Docker 模式的数据目录是 compose 里挂载的 `${DATA_DIR:-./data}`
（部署时通常是 `/opt/mcsync/data`），搬同一个目录即可；注意 `.env` 里的
`HOST_PORT` 也要一起带过去，否则容器端口映射会变。

### 迁移后的验证清单

1. `sudo bash deploy.sh --status` 显示的端口与旧机一致
2. 浏览器登管理页 → 存档数量、每个存档的版本数、整合包分组都对得上
3. 随便下载一个存档 zip，能正常解开且 `level.dat` 可读
4. 客户端改地址后能列出云端存档，上传一个小改动只补传少量数据块
   （说明 blob 索引与内容都完整）

## 五、它是怎么省带宽的

| 机制 | 说明 |
|---|---|
| **两级哈希预筛** | 先比「文件大小 + 修改时间（毫秒）」，一致就直接复用上次算好的哈希，不读盘；需要时才用 xxHash（比 SHA256 快一个量级）计算 |
| **4 MiB 内容寻址分块** | 文件被切成 4 MiB 的块，只传云端没有的块。改了一个 100 MB 存档里的一小段，通常只传几 MB |
| **秒传** | 云端已存在相同内容（换机器、重装、回滚）时，一个字节都不用传 |
| **本地块缓存** | 下载过的块缓存在本地，再次下载其他版本时直接复用 |
| **并发 + 断点续传** | 默认 4 线程并发；中断后重来，已传的块自动跳过，从没传的部分继续 |
| **智能忽略** | 默认跳过 `session.lock`、`*.tmp`、`logs/`、`crash-reports/` 等无意义或易变文件，规则可在设置里追加 |

每次同步都会生成一个**版本快照**，可随时回滚；本地与云端同时改了同一个文件时，会弹窗让你逐个选择「用本地 / 用云端 / 都保留」，覆盖前还会自动做**硬链接备份**（几乎不占空间）。

## 七、安全机制

部署时自动生成 **16 位随机配对口令** 与 **随机高位端口**，写入 `${INSTALL_DIR}/mcsync.env`（权限 0600）。

四道防线：

| 防线 | 做法 |
|---|---|
| 配对口令 | 16 位（62 字符集，约 95 bit 熵），仅在「客户端配对 / 管理页登录」时出示 |
| 客户端私钥 | 配对成功后，客户端用本地生成的 32 字节密钥对每个请求做 **HMAC-SHA256 签名**；此后口令不再传输，私钥永不上网 |
| 重放防护 | 时间戳窗口 ±300s + 一次性 nonce，签名覆盖 `ts/nonce/METHOD/path/body-sha256`，body 被篡改即失败 |
| 暴力防护 | 同 IP 10 分钟内失败 10 次即锁定 10 分钟；可选 IP 白名单（支持 CIDR） |

另外：启用鉴权时 **关闭 `/api/docs` 与 OpenAPI 结构**，响应统一加 `nosniff` / `DENY` / `no-referrer` / `no-store`，
管理页会话为 HttpOnly + SameSite=Lax Cookie，口令轮换或撤销客户端立即生效。

**客户端怎么用**：设置 → 填「登录账号 + 口令」（管理员在面板创建）→ 自动登录（只需一次）。
之后每次同步都用本机私钥签名，口令不再传输。换机器就再登录一次，互不干扰。

**运维命令**：
```bash
sudo bash deploy.sh --show-token        # 找回管理员密钥
sudo bash deploy.sh --rotate-token      # 换口令（会撤销所有客户端，需重新配对）
sudo bash deploy.sh --revoke-clients    # 撤销全部客户端
sudo bash deploy.sh --allow-ip 1.2.3.4  # 追加 IP 白名单
```

**建议**：公网长期使用时，前面套 Nginx 做 HTTPS 反向代理，并设 `MCSYNC_TRUST_PROXY=1` 让服务端识别真实 IP。

## 八、常见问题

**Q：换了服务器 / 旧服务器 IP 失效后，客户端双击没反应，连改地址的地方都没有？**
这是旧版本的启动死锁：`App` 构造时在界面主线程同步去连配置里的旧地址，
主 session 挂了 5 次重试；云服务器对已释放的 IP 通常**直接丢包**（不是拒绝），
Windows 的 TCP SYN 重传本身就要 20 秒，叠加重试能卡 100 秒以上。
构造不返回，登录窗口就没机会创建，主窗口又处于隐藏状态 —— 屏幕上什么都没有。

已修复，现在的行为：

- **启动阶段零网络请求**：主界面先显示，身份确认和连接探测全部放后台
- 探测用独立 session，**连接 2.5 秒 / 读取 6 秒短超时、零重试**，不可达就几秒内放弃
- 登录页地址框始终可编辑；自动登录等太久可点「**停止自动登录，修改地址**」
- 连不上时会明确提示「无法连接原服务器 …，请修改服务器地址后重新登录」，并把光标放到地址框
- 万一主界面自身崩了，会弹出一个只依赖标准库的「**紧急设置**」窗口，仍能改地址 / 清空登录状态

直接在新地址登录即可。`accounts.json` / `clients.json` 随服务端迁移过来的话，
只有服务器地址需要改，账号口令不用重填。

**Q：导入了新整合包，全盘重扫 / 实例重扫都找不到？**
旧版有四个叠加原因，现已全部修复：① 候选根只认名字含 `pcl/hmcl/minecraft/mc` 等
关键词的目录，「E:\整合包\ATM9」这种任意名字的文件夹永远不在扫描范围；② 判断游戏目录
时强制要求 `saves` 存在，而刚导入、还没进过游戏的实例只有 `mods/ + versions/`；
③ 遍历时跳过了候选根自身，用户手动添加的「实例目录本身」扫不到；④ 每个根只给 4000
目录预算，浅层就耗尽，把深度调大也没用。

现在：盘符第一层目录**不论名字**都纳入候选（明确候选优先扫、广谱根后扫，两批独立预算），
无 `saves` 的新实例也能识别，**扫描深度默认 6、上限 12** 且真正生效。仍找不到就点
左侧 **➕** 直接选那个整合包目录——添加后**当场深扫并落盘**，不用重启软件；也可以在
「设置 → 连接」把上层目录写进「额外实例目录」，调大深度后全盘重扫。

**Q：客户端报 "too many 503 error responses"，但服务器明明是好的？**
这曾经是系统代理劫持（Clash / v2ray 会设 `HTTP_PROXY=127.0.0.1:7890` 或 `10808`）。
**现在客户端强制直连、不设任何代理开关**：连自己的服务器不需要代理，走本地代理反而连不上。
需要代理的是把源码推到 GitHub 的 `push.bat`（默认走 10808，可用 `--no-proxy` 关闭），
那是 git 侧的事，与客户端无关。若连不上服务器，请检查地址、端口与云服务器安全组。

**Q：上传报 "有 N 个数据块上传失败"？**
说明个别块连续 3 轮都没传上去。客户端会自动补传并复查，仍失败才报错。
通常是网络抖动或代理干扰，重试即可；换更稳定的网络或调低并发线程数也有效。

**Q：下载时 40MB 的存档却显示「要下载 5.2G」，进度条一直走不满？**
旧版用「固定块大小 4MiB × 分片数」估算下载总量，但分片是自适应 / region 覆盖式
切分的，一块常常只有 32KB~256KB。一个 40MB 存档若切成 1300 个 region 小分片，
`4MiB × 1300 = 5.2GiB` —— 分母虚高 128 倍，实际只下 40MB（压缩后更少），
进度条自然永远停在 0.8%，ETA 也按虚高分母算得离谱；`total_items` 还被累加成两倍。

已修复：改用云端清单里**每个分片的真实长度**求和（分片有序不重叠、总长恰好等于
文件大小，所以合计就是存档实际大小），替换而非累加进度分母，并按服务端压缩后
blob 的实际字节动态校准，进度条能正常走到 100%。

还有一种更隐蔽但更危险的情况：**云端某个历史版本本身就是旧版客户端上传的
膨胀分片**（曾出现 400MB 存档清单记了 16GB）。这种情况下"显示 5.2G"是真的会
下载 5.2G，且组装时长度对不上会写坏档。现在下载前会体检清单，命中即中止并
给出人话提示；处理办法是在管理面板删除该历史版本，或重新上传一次生成新版本，
然后点「🧹 清理冗余」回收磁盘。

**Q：朋友设备上「云端存档 → 版本 → 下载」弹窗显示不全，底部按钮点不到？**
旧版那个弹窗（以及确认框、归类框、输入框、紧急设置窗口）用的是固定 `geometry`
加一串 `pack()`：在开发机上刚好够，但高 DPI 缩放 / 大字号 / 小屏笔记本上每行都变高，
内容总高超过窗口，底部「开始下载 / 取消」直接被裁掉，而且既不能滚也拉不大。
另外 `wraplength=500` 这类写死像素，在窗口被夹窄时文字会从右侧溢出。

现在所有对话框统一走公共底座：内容放进可滚动容器、按钮栏固定在窗口底部不随内容
滚走、构造完按实际内容尺寸自动撑高撑宽（不超过屏幕可用高度）、`wraplength` 跟随窗口宽度
动态更新；主窗口 `minsize` 和紧急设置窗口也按屏幕可用空间收缩。
`client/ui/design.py` 的 `auto_wrap_label` / `auto_wrap_tree` 把主窗口各页、卡片里
散落的固定像素换行统一收口，不同分辨率与缩放比例下表现一致。

**「UUID 修复」确认框又显示不全 → 找到的最后一层根因**：Tk 的 `pack` 按 **pack 顺序**
分配空间，先 pack 的控件先拿它请求的尺寸。旧版可滚动 `body` 在底座构造时先
`pack(fill=both, expand=True)`，`footer` 却在子类构造末尾才 `pack(side=bottom)`；
内容一多（确认框的 message 带空行、extra 带长路径），body 先把空间吃满，
后到的底栏被直接挤出窗口下沿 —— 滚动也救不回来，因为它压根不在可视区。
现在 `footer` 在底座里**第一个** pack，`body` 排在其后；`make_footer()` 只返回
这个已有容器，绝不再新建 Frame。同时 `_fit_content()` 会先按窗口宽度定换行、
再量内容高度，把窗口撑到「刚好装得下」（实测 260 → 350）。

### UI 架构：customtkinter 6.0.0 统一方案

全项目 UI 只有一套标准：版本钉死 `customtkinter==6.0.0`，**不再在 5.x / 6.x
之间切换**，也不再有任何运行期兼容层、版本探测、降级窗口或原生 tkinter
应急框。

| 文件 | 职责 |
|---|---|
| `ui/design.py` | 间距刻度（4/8/12/16/24/32）、字号、圆角、配色令牌 |
| `ui/theme.py` | 主题切换、CTkFont、DPI 缩放（`set_widget_scaling` + 6.0 的 `set_window_scaling`） |
| `ui/dialogs.py` | 唯一的 `_BaseDialog` 底座 + 7 个对话框，全部 CTk 原生控件 |
| `ui/main_window.py` / `login_window.py` / `widgets.py` / 各页面 | 业务界面 |

底座统一负责：`footer` 先 `pack(side="bottom")`、`body` 后
`pack(fill=both, expand=True)`；`wraplength` 跟随窗口宽度；按内容自适应
尺寸；窗口 map 后才抓 grab，`_close()` 幂等释放。各对话框只往
`body` / `footer` 放控件，不自己管窗口。

### 总根因：`self._w` 是 tkinter 的 widget path

连续多版「窗口打不开 / 弹提示框 / 按钮消失 /
`TclError: bad window path name "720"`」，根因**不是 customtkinter 版本**：
底座里写了 `self._w = 720` 存宽度，把 tkinter 内部保存窗口路径的属性覆盖成
数字。之后所有 Tcl 命令都拿 `"720"` 当窗口名，控件构造全线失败。

之前为这个错误加的降级链、原生 tkinter 应急窗口、版本强制校正、矢量
Canvas 按钮，全是在治标，越堆越乱。现在：

- 宽高改用 `_dlg_w` / `_dlg_h`，**绝不碰 `_w` / `_h`**
- 删掉 `ui/tk_compat.py` 等全部兼容层与 `_native_*` 降级实现
- `requirements.txt` 与 `build.py` 都钉死 6.0.0；`build.py` 只校验版本，
  不再 `force-reinstall`、不再清缓存猜版本

### 明暗切换按钮

纯 `CTkButton`，`width=height=28` 固定正方形，与设置按钮同一容器、同一
`pack(side="left")`，位置和大小完全一致；文字用几何符号 `◐` / `◑`
（深色 / 浅色），不是 emoji，不会被字体回退拉扁；`rebuild_ui()` 重建时
自动跟随主题。

### 自检与构建门禁

`tools/test_ui_layout.py` 33 项：8 种屏幕 / DPI × 7 个对话框逐个构造，
验证 footer 顺序、按钮存在、窗口不超屏；另有源码护栏断言「无兼容层 /
降级 / 版本切换」「不覆盖 `_w`」「版本钉 6.0.0」「主题按钮固定正方形」。
`build.bat` 每次打包前强制跑。

**门禁只对明确的布局断言 `[FAIL]` 中止**；自检脚本自身崩溃、超时、无输出、
编码问题一律打警告继续构建 —— 工具链不该挡住交付。逃生开关
`build.bat --no-ui-check`。

### build.bat 被「UI 布局自检」挡住，日志停在满屏 `[OK]`

**先说结论：UI 自检现在不会再因为工具链自身的问题挡住构建。**

事故现场（`tools/_ui_layout_last.log`）：

```
[5] 模态安全（窗口弹不出来 / 软件关不掉）
  [OK] 构造期不抓 grab ...
  ...
  [OK] _close 幂等（重复调用不抛异常）
（到此戛然而止 —— 没有汇总行、没有 traceback、没有 [FAIL]）
```

沙盒里 `[5]` 节应有 22 项，Windows 上只打了 8 项就断了：脚本在
「构造中途异常 → 应急原生窗口」那段崩了（该路径依赖真实 Tk 行为），
**根本没跑到汇总**。而旧版 `build.py` 把这个 `rc!=0` 一律当成
「布局不合规」，还把最后 22 行当失败原因打印 → 满屏 `[OK]` 配一句
「已中止构建」，完全误导。

这已经是同一个门禁第 N 次因**自身**故障挡住交付（前面还有 GBK 管道
编码崩溃）。用户要的是 exe，不是看自检全绿。所以改了三条：

| 情形 | 处理 |
|---|---|
| `rc=0` + 有汇总行 | 正常通过 |
| **明确的布局断言 `[FAIL]`** | 中止（这是唯一该拦的情况，仍可 `--no-ui-check` 放行） |
| 脚本自身异常 / 超时 / 无汇总行 / 无输出 / 编码崩溃 | **打警告、写日志、继续构建** |

配套：

- `build.bat --no-ui-check`：连布局断言失败也只警告，彻底不挡路
- `preflight_ui_layout` 失败时会明确说「这是自检工具的问题，不是布局问题 —— 已放行继续构建」，并指出**在第几节后中断**、日志路径、单独排查命令
- 自检脚本顶层兜底现在输出 `[FAIL] SELFCHECK_CRASHED at: <最后一项>`，不再静默消失
- `[5]` 那段应急窗口构造加了环境隔离：真出兼容性问题只打一条 `[SKIP]` 并继续，绝不牵连后面的节和最终汇总行
- 完整自检仍可手动跑：`python tools/test_ui_layout.py`

`tools/test_ui_gate.py` 30 项用 monkeypatch 模拟各种子进程结局：全绿、
日志停在 `[5]`、无输出、GBK 崩溃、`rc=2`、模块缺失、超时 → 全部放行；
只有带 `[FAIL] 底栏被挤出窗口` 这类明确断言才中止；`--no-ui-check` 一律放行。

> **这次覆盖源码后直接 `build.bat` 即可**，不会再被这个门禁挡住。
> 万一还看到工具链警告，构建仍会继续到 PyInstaller；想干净跳过就加
> `--no-ui-check`。

### build.bat 报「UI 布局自检未通过」但中间一片空白

```
  [*] UI 布局自检（多分辨率 / DPI 缩放）...
  [X] UI 布局自检未通过，已中止构建：


       修好布局后重新运行 build.bat；自检细节见 tools/test_ui_layout.py
```

**这通常不是布局坏了**，而是自检脚本自己崩了。原因很隐蔽：

`build.py` 用 `subprocess.run(capture_output=True)` 起自检子进程。父进程直接
print 到控制台时中文正常，但**子进程 stdout 被重定向到管道后，Windows
Python 会改用 locale 编码 GBK/CP936**。而 `tools/test_ui_layout.py` 打印
`✅` / `❌` → 第一个 check 就抛

```
UnicodeEncodeError: 'gbk' codec can't encode character '\u2705'
```

脚本当场退出、rc=1、有效输出几乎为空。门禁只看到「未通过」，连失败项都
打不出来 —— 看起来像布局回归，实际跟布局毫无关系。Linux UTF-8 沙盒里
永远测不出来，所以之前几轮全绿、一到 Windows 就炸。

修复三层：

| 层 | 内容 |
|---|---|
| 自检脚本 | 开头 `_safe_stdio()` 把 stdout/stderr 重配置成 UTF-8 + `errors="replace"`；所有状态标记改成纯 ASCII `[OK]` / `[FAIL]`；顶层 `except BaseException` 用 `backslashreplace` 打 ASCII-safe traceback |
| 构建脚本 | 子进程注入 `PYTHONIOENCODING=utf-8` + `PYTHONUTF8=1`，加 `-u` 无缓冲，父进程按 UTF-8 解码，两边编码一致 |
| 失败诊断 | 不再只打最后 22 行：区分「自检自身崩溃」与「布局不合规」，前者列出 Error/Traceback 行并给出手动运行命令，后者列出 `[FAIL]` 行；完整输出写到 `tools/_ui_layout_last.log` |

`tools/test_selfcheck_encoding.py` 33 项：先在 GBK 管道下**复现**
`UnicodeEncodeError`，再用 `utf-8 / gbk / ascii / cp936` 四种 `PYTHONIOENCODING`
真正跑一遍自检，断言 rc=0、有成功摘要、无编码异常；再做反向验证（去掉
`_safe_stdio` + 换回 emoji 后，GBK 下必须再次崩且跑不完）。

> 重新覆盖源码后再跑 `build.bat`，应看到
> `[OK] 全部 34 项通过 — 7 个对话框 × 8 种屏幕规格均无显示不全`
> 并正常进入 PyInstaller。

**Q：上传报 409 missing_chunks，且 sample 里是同一个哈希重复出现？**
存档里有 **0 字节空文件**。旧版本会把空文件的"整文件哈希"（xxh128 空内容 = `99aa06d3...`）当成数据块写进清单，
但空文件不产生任何块，云端自然没有 → 409。已修复：空文件不再产生数据块，服务端也不再为它补哈希。

**Q：客户端提示"认证失败 / 该客户端未登记"？**
现在用**账号登录**（不再是服务端随机口令）：账号由管理员在 Web 面板「账号管理」里创建，
登录窗口或「设置 → 连接」里填账号 + 口令即可。登录后本机生成私钥，之后请求一律用私钥
签名，口令不再传输。管理员密钥只在创建第一个管理员账号时用一次。

**Q：登录成功后左上角还显示"未连接"？**
旧版状态栏只在启动时探测一次，之后手动登录也不刷新。现在登录成功会立刻更新为
「● 已连接」并重新测延迟，多次探测用代次保护，过期结果不会把状态覆盖回去。

**Q：客户端每次启动都要扫很久？**
首次启动做一次全盘扫描，之后直接读取已保存的实例路径（毫秒级）恢复列表，界面立即可用；
随后在**后台静默重扫一次已知目录**（不禁用按钮、结果没变化就不写日志），可到
「设置 → 连接 → 启动时自动刷新」关掉。想找全新位置的实例点「🔍 全盘重扫」；
只刷新已有实例点「⟳ 实例重扫」。重扫结果都会与缓存合并并落盘，不会刷新回原样，
已失效的路径会自动剔除。

**Q：服务器地址填了没保存？**
地址栏回车、失焦、点「连接测试」都会立即落盘，退出时也会再存一次，下次启动自动回填。

**Q：脚本打印的端口和实际能连上的不一样？**
新版部署会做三重保障：systemd 单元里 `Environment=` 显式写端口（不依赖 env 文件权限）、
`ExecStart` 带 `--port`、部署完成后**实测探测真实监听端口**并以实际值为准显示。
同时会清掉旧版本残留的服务进程（老服务常占着 8650）。
若仍不一致，脚本会明确提示并给出 `systemctl status` / `journalctl` 排查命令。

**Q：切换主题后界面一半深一半浅？**
已改为切换时**整体重建界面**。程序里大量控件显式指定了颜色，不会跟随
`set_appearance_mode` 自动变化，逐个改色必然有遗漏，重建是最彻底的做法。
重建会保留实例/存档/云端列表与选中项，不影响使用。

**Q：扫描很慢、CPU 和磁盘都没跑满？**
三处优化：`os.scandir` 替代 `listdir + isdir`（省掉逐项 stat）、
跳过 Program Files / node_modules 等无关目录树、多个根目录与多个存档**并行处理**。
首次全盘扫描后结果会缓存，之后启动直接复用，不再遍历磁盘。

**Q：配置文件存在哪？**
系统级应用数据目录，**不是程序所在目录**：
`%LOCALAPPDATA%\MCSync\config.json`（Windows）、`~/.config/MCSync/config.json`（Linux）。
旧版本放在 exe 同目录，升级后会自动迁移过去，不会丢配置。
可用环境变量 `MCSYNC_CONFIG_DIR` 覆盖。

**Q：设置页里配对口令输入框点不到 / 输不进去？**
已修复。旧版本「连接」页里 `row=1` 和 `row=4` 各被两个控件占用，
后放置的控件盖住了口令框，导致点不到也输入不进去。现在每个 grid 行只放一组控件，行号严格递增。

**Q：老存档点「管理」提示私钥验证失败？**
已修复。根因是签名基串里路径的编码形态不一致：客户端按 HTTP 请求行签名（百分号编码，
如 `/api/save/%E6%88%91.../versions`），服务端 ASGI 拿到的是解码后的路径
`/api/save/我的世界存档/versions`，两者 HMAC 不同 → `bad_sign`。
纯英文名的存档不受影响，所以表现为"新上传的能管理、中文名/带空格的老存档不能"。
服务端现在会尝试路径的所有等价形式，老客户端与新客户端都能正常访问。

**Q：开启鉴权后能上传但下载报 401？**
已修复。数据块下载接口漏了签名头（上传接口有、下载接口没有），
自测用关闭鉴权的环境跑，所以这个 bug 一直没暴露。现已补齐。

**Q：云端存档怎么和整合包对应？**
上传时客户端会把当前实例名（整合包名）一起提交，云端按整合包**分组显示**：
「📦 1.20.1-Forge」下挂它自己的存档，「📦 1.12.2-Forge」下挂它自己的。
老存档（没有整合包信息）归入「🗂 未分类」，可点云端面板的「🏷 归类」手动指定归属。

**Q：两个整合包里有同名的存档会混吗？**
不会。同名存档分属不同整合包时，服务端自动另建一条（显示为「MyWorld (1.12.2-Forge)」），
两边各自独立计版本、独立下载，原记录不受影响。

**Q：云端列表为什么不再显示 v1/v2？**
版本号是**单个存档自己**的上传序号，不同存档的 v1 互不相干，并列展示会让人
误以为它们是同一套版本。现在列表主标识改为「整合包 · 存档名 + 更新时间」，
版本号只在点开「版本管理」后以「第 N 版」出现。

**Q：连不上服务器 / 一直超时？**

**客户端始终直连，不走任何代理**——连自己的服务器不需要代理，
系统里装的 Clash / v2ray 反而会把流量劫持走导致失败。

排查顺序：
1. 服务器地址与端口是否正确（部署完会打印，端口是**随机高位端口**）
2. 云服务器**安全组是否放行了该 TCP 端口**（阿里云/腾讯云控制台里加）
3. 服务是否活着：`systemctl status mcsync` / `journalctl -u mcsync -f`
4. 本机防火墙是否拦截

> 需要代理的是 **push.bat 推 GitHub**，那是 git 的事，默认走
> `http://127.0.0.1:10808`。换端口用 `--proxy`，不走代理用 `--no-proxy`，
> 只测代理通不通用 `--check-proxy`。

**Q：连不上服务器？**
先在服务器上看 `bash deploy.sh --status`，再确认端口已放行（`ufw allow 8650/tcp` 或云厂商安全组）。

**Q：同步会不会把存档弄坏？**
覆盖前会自动硬链接备份；每次同步都是新版本，旧版本不会被覆盖，随时可回滚。只有在你明确选择「用云端」时本地才会被覆盖。

**Q：部署完显示的 IP 不对，客户端该怎么填？**
服务器在内网时脚本显示的是局域网 IP，**客户端在另一台机器必须填公网 IP**。
脚本会优先探测公网 IP（云厂商元数据 → 公网回显服务），探测不到会明确提示。
事后可随时用 `sudo bash deploy.sh --status` 再看，或用
`sudo bash deploy.sh --public-ip 1.2.3.4` 手动指定。

**Q：多人共用一台服务器？**
当前是免认证单空间模式（适合家庭 / 小团队可信环境）。需要多人隔离可以给服务端加一层反向代理的 Basic Auth。
